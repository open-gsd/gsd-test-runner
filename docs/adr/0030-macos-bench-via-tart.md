# ADR-0030 — Revisiting macOS Bench: Tart as the macOS-native runtime

**Date**: 2026-09-06
**Status**: Accepted (2026-09-06) — direction locked (Tart, additive, per Decisions 1-2, 5). Decisions 3-4's mechanics went through three spikes on 2026-09-06: documentation (Phase 0), a live end-to-end test against a real Apple Silicon Mac (Phase 1), and root-cause research into a failure Phase 1 found (Phase 2). Net outcome: Decision 4's exec transport is now **SSH, not `tart exec`** — see Decision 4 for why. Decision 3's image-distribution mechanics and Decision 5's memory cap are confirmed working; the custom-image bake process is the one piece still genuinely unverified.
**Context**: Architecture review — revisits ADR-0020 (macOS Bench via Apple Containers, amended 2026-05-24 to Docker-on-macOS) in light of Apple Containers' confirmed architectural ceiling, the now-resolved macOS 26 availability blocker, and a recurring host-out-of-memory failure mode on the current bare-metal macOS Runner. Tracked in a Feature Request issue per `CONTRIBUTING.md`, referencing this ADR.

## Context

ADR-0020 (2026-05-23) originally chose Apple Containers (the `container` CLI) as the macOS Bench runtime, then amended itself one day later to Docker-on-macOS (Docker Desktop / colima running the Linux Tester Image) because Apple Containers required macOS 26, which was not yet generally available on developer Macs or GitHub Actions runners. The amendment explicitly preserved `bench.Bench`'s `Runtime` field and the `RuntimeContainer` constant "for that future" — the path back to Apple Containers was left open, gated only on macOS 26 availability.

Research conducted since (Context7 docs for `apple/container`, plus a fanned-out, adversarially-verified web research pass, September 2026) closes that gate permanently rather than opening it, while surfacing a better path:

1. **macOS 26 availability is no longer the blocker.** GitHub Actions macOS 26 hosted runners reached general availability on 2026-02-26 (public beta since 2025-09-11), and `macos-latest` itself began defaulting to macOS 26 in a rollout completing by mid-July 2026. If Apple Containers' only problem had been runner availability, ADR-0020 could simply flip back today.

2. **It cannot flip back, because Apple Containers is architecturally Linux-guest-only.** Apple's own `container` README and the underlying `containerization` Swift package state, and a live re-fetch in September 2026 reconfirmed verbatim, that every container is a lightweight **Linux** VM. The CLI's `--os` flag defaults to `"linux"`; the backing service is named `RuntimeLinux`. No macOS-guest mode exists, and no Apple roadmap or announcement suggests one is coming — a Hacker News thread discussing the tool speculates Apple's omission of native macOS-on-macOS containerization ("Darwin jails") is a deliberate business decision, not an oversight. Separately, the `macos-26` GitHub-hosted runner image doesn't even ship `container` preinstalled (open feature request in `actions/runner-images`), so even the container*-tooling* convenience Apple Containers might have offered isn't there out of the box. This means the original issue #8 ask — "test macOS-based products on macOS hardware, running macOS as the guest" — is permanently out of reach for Apple Containers, independent of any future macOS version.

3. **Docker-on-macOS (the current decision) has the same guest-OS ceiling.** It solves "container isolation from the Mac filesystem" (the amendment's actual stated requirement), but the Linux Tester Image running inside it still cannot exercise FSEvents, case-insensitive HFS+ semantics, or macOS-only Node/system APIs — the amendment's own Consequences section says as much.

4. **A real, separate operational problem exists that neither option fixes:** the current macOS Runner (the transitional `gsd-test-local` script, per `CONTEXT.md`) runs bare-metal `node --test` with **no memory ceiling**. The Linux and Windows Docker Benches have carried a memory cap since ADR-0021 (`internal/dispatch.DefaultMemory`, baked into `DockerRunArgs`) — a leaking or fork-bombing test is bounded by the container's own memory limit and gets reaped, never touching the Bench's real RAM. The macOS Runner has no equivalent. A test that spawns runaway children on bare metal has repeatedly run the host Mac out of memory. Docker-on-macOS would inherit the existing container memory cap, but only for the Linux guest — it does not, by itself, fix the bare-metal-Runner failure mode for anyone who still needs real macOS execution outside a Linux container.

5. **Apple's Virtualization.framework can do both at once.** `VZMacOSInstaller`/`VZMacPlatformConfiguration` boot genuine macOS as the guest, and `VZVirtualMachineConfiguration.memorySize` is a hard, hypervisor-enforced allocation — bounded by `VZVirtualMachineConfiguration.minimumAllowedMemorySize`/`.maximumAllowedMemorySize` and the target macOS build's own `VZMacOSConfigurationRequirements.minimumSupportedMemorySize`. Once the VM is running, a runaway process inside it is capped at that allocation; it cannot balloon into the host's memory the way a bare-metal process can. This is the same protective shape `DefaultMemory` gives the Docker Benches, but for a real macOS guest instead of a Linux one.

6. **Tart** (Cirrus Labs, `github.com/cirruslabs/tart`) is a mature, actively-maintained CLI wrapping exactly this: prebuilt macOS base images (including macOS 26 "Tahoe" images), `tart set --memory <MB>` for a hard per-VM cap, and APFS-clone-based ephemeral VM creation (`tart clone` + `tart run`) that is fast enough to spin up per-run — the same shape as this repo's existing "fresh container per run" model (ADR-0002's PR-merged worktree, ADR-0021's run-and-die). Hand-rolling Virtualization.framework directly would mean owning restore-image downloads, `VZMacAuxiliaryStorage` provisioning, and snapshot/revert lifecycle ourselves; Tart already does this and is the tool practitioners in this exact space (macOS CI on Apple Silicon) have converged on.

7. **Licensing is not a blocker for this project's Bench model.** Apple's macOS Software License Agreement (checked against the Tahoe 26 SLA, consistent with prior SLA versions back to Mac OS X Lion) permits running up to two additional macOS instances in a virtual environment, on Apple-branded hardware the licensee owns or controls, for software development, testing-during-development, or personal non-commercial use. gsd-test-runner's Bench model (ADR-0007) is already "the developer's own hardware, used to test during development" — squarely the licensed use. It would not cover, for example, a shared multi-tenant cloud pool of macOS VMs running on non-Apple hardware or beyond two instances per physical Mac; this ADR does not propose that shape.

## Decisions

### Decision 1 — Add a third macOS runtime: Tart, not Apple Containers

Apple Containers is not pursued further as a macOS Bench runtime. This is a permanent conclusion, not a version-gated deferral like ADR-0020's original text — the blocker is architectural (Linux-guest-only), not availability, so no future macOS release resolves it on its own. `RuntimeContainer` and the `Runtime` field on `bench.Bench` are **not removed**; they cost nothing to keep and stand as a record that the path was seriously evaluated twice (ADR-0020 and here) before being rejected on its merits both times.

Add a new sentinel, `RuntimeTart = "tart"`, alongside `RuntimeDocker` and `RuntimeContainer` on `bench.Bench` (`internal/config/config.go`, `internal/bench`). This is the path that actually answers issue #8's original ask: test macOS-based products on macOS hardware, with macOS itself as the sandboxed guest.

### Decision 2 — Tart is an additive opt-in, not a replacement for Docker-on-macOS

A macOS Bench may run `RuntimeDocker` (ADR-0020's current behavior: Linux Tester Image, filesystem isolation only, zero extra setup) or `RuntimeTart` (this ADR: real macOS guest, memory-capped, requires a prepared Tart base VM image on the Bench). This is a per-Bench config choice, same shape as the existing `Runtime` field. Docker-on-macOS remains the zero-friction default for anyone who only needs filesystem isolation; `RuntimeTart` is the upgrade path for projects that actually exercise macOS-native code paths or have been hit by the bare-metal-Runner OOM failure mode.

### Decision 3 — Tester Image distribution for Tart: OCI registry, resolved

**(Resolved 2026-09-06; Phase 0 documentation spike, corrected 2026-09-06 by a Phase 1 hands-on spike against a real Mac.)** Tart images distribute exactly like Docker images at the registry layer: `tart push <local-vm> <registry>/<repo>:<tag>` and `tart pull <registry>/<repo>:<tag>` operate against any standard OCI registry, GHCR included — the existing GHCR-distribution story (ADR-0005) extends here unchanged. `gsd-tester-macos-tart:vX.Y.Z` is a real, independently-built Tart image (Node + Reporter baked in, on top of a Cirrus Labs base image — see Decision 4), not an alias of the Linux image the way today's Docker-on-macOS path is.

**Correction to the Phase 0 pass:** that earlier text claimed Tart has no OCI-label mechanism at all. That was wrong. `tart push` (Tart 2.32.1, verified via `tart push --help` on real hardware) takes a repeatable `--label <key>=<value>` flag — "additional metadata to attach to the OCI image configuration in key=value format." So the ADR-0011 version sentinel likely **can** be a real OCI label after all: `tart push gsd-tester-macos-tart ghcr.io/open-gsd/gsd-tester-macos-tart:vX.Y.Z --label sh.gsd-test.image-version=vX.Y.Z`, the same shape Docker uses.

**Read side — now confirmed negative, not just unconfirmed.** A real `ghcr.io/cirruslabs/macos-tahoe-base:latest` image (27.3 GB compressed, 50 GB on disk) was pulled and cloned on real hardware. `tart get <name> --format json` on the clone returns only Tart's own local VM config — `Display`, `Memory`, `OS` (`"darwin"` for a macOS guest — itself a useful confirmed fact, Tart's own model tracks guest OS type explicitly), `Disk`, `Size`, `DiskFormat`, `State`, `CPU`, `Running`. No labels field, confirmed empirically, not just absent from `--help`. So the OCI `--label` written at push time does **not** round-trip through `tart get` after a pull — reading it back would need a lower-level OCI manifest inspection (`crane`/`skopeo`/raw registry API) outside `tart` itself, unconfirmed whether that's worth the extra dependency. **Plan A is now "real OCI label, but read back via a manifest tool, not `tart get`"; the Phase 0 fallback (an in-guest sentinel file, read via `tart exec`) remains Plan B** — and Plan B currently carries the same open risk `tart exec` itself does (see Decision 4's correction below).

**Also newly confirmed:** `tart clone`/`tart pull` do automatic local-cache pruning to fit the incoming image (`TART_NO_AUTO_PRUNE` to disable, `--prune-limit` on clone to cap it) — worth knowing before scripting unattended pulls on a Bench with limited disk. The pull itself completed cleanly in a few minutes with no issues once real disk headroom was confirmed (see the Consequences note on the Phase 1 host's disk-space false alarm).

**Still not verified hands-on:** the exact bake process for a custom Tart image (`tart run` + interactive setup + `tart stop` + `tart push`, or something more scriptable). The pull/clone/config-read mechanics above are now real, verified facts; baking a *custom* image with Node + Reporter installed was not attempted in this pass.

### Decision 4 — Execution transport for Tart: pivot to SSH; `tart exec` reliability unresolved and not required

**(Phase 0 documentation spike resolved this 2026-09-06 as `tart exec`; a Phase 1 live end-to-end test the same day found a reproducible failure; a Phase 2 root-cause research pass, also 2026-09-06, could not confirm the mechanism but found a decisive precedent. Net result: this ADR now recommends SSH, not `tart exec`, as the exec transport.)**

`tart exec [-i] [-t] <name> <command> ...`, backed by the Tart Guest Agent's gRPC RPC service, is real and its CLI shape genuinely mirrors `docker exec -i`/`-t` closely enough to fit `internal/dockerexec`'s existing `Run`/`Stream` signatures — that part of the original plan was sound. But a live test against a real, freshly-pulled `ghcr.io/cirruslabs/macos-tahoe-base:latest` guest, booted headless (`tart run --no-graphics`), consistently failed: every `tart exec` attempt returned **exit 125 with completely empty stdout and stderr**, even though the Guest Agent was confirmed running with `--run-agent` (implying the RPC service is up) and everything else about the VM worked — it booted, got an IP, and was directly SSH-reachable with Cirrus Labs' documented default `admin`/`admin` credentials.

**Root-cause research (web search + adversarial verification, 2026-09-06) could not pin down the exact mechanism, but found the decisive fact for this decision anyway.** The two previously-real `tart exec` bugs (a non-TTY crash, a hardcoded RPC timeout) were both fixed 6–10 months before the Tart version used here and both produced visible error text — neither matches this repro's silent empty output, so both are ruled out. The leading hypothesis — a macOS Local Network Privacy/TCC permission gate silently blocking the Virtualization.framework path to the guest agent's RPC service in a headless, no-GUI-session context — is a real, Apple-DTS-acknowledged class of failure and is specifically documented for a *different* Cirrus Labs tool (`gitlab-tart-executor`) on Sequoia+ hosts, but was not directly confirmed as `tart exec`'s specific failure mechanism; treat it as the working explanation, not a proven one.

**What settles Decision 4 regardless of that unresolved mechanism: Cirrus Labs' own reference CI integration, `gitlab-tart-executor`, does not use `tart exec` at all.** Its entire in-guest execution path is SSH — the same default `admin`/`admin` credentials this ADR already confirmed work — with `tart clone`/`set`/`run` used only for VM lifecycle. That is Cirrus Labs' own dogfooded, production answer to exactly this "run commands in a headless CI-managed Tart VM" problem, and it sidesteps the entire unresolved question rather than requiring it to be answered.

**Decision, revised:** `RuntimeTart`'s exec transport is **SSH**, not `tart exec`. This reverses the "third case in the existing `dockerexec` switch" expectation from the Phase 0/Phase 1 passes: SSH's connect/auth/session shape doesn't fit `dockerexec.Run`/`Stream`'s docker-subprocess-argv model, so a `RuntimeTart` case most likely needs its own small SSH-based leg implementation (`golang.org/x/crypto/ssh`, or shelling out to `ssh`/`scp` the way `DockerHost()` already builds an `ssh://` transport string for remote Docker Benches per ADR-0011) rather than extending `dockerexec` in place — landing back on the `internal/tartexec`-shaped path ADR-0020 Decision 2 originally considered and rejected for Apple Containers, but for a different, now-confirmed reason.

This is not a dead end for `tart exec` forever — if a future spike (with VNC-attached boot to see whether a permission dialog is actually the cause, and Tart's own recommended `log stream --predicate='process==tart OR process CONTAINS Virtualization'` live capture, not the retrospective `log show` this pass used) resolves the underlying mechanism, revisit. But there is no reason to block `RuntimeTart` implementation on that when a proven, Cirrus-Labs-sanctioned alternative already exists.

**Copy-in mechanism (`--dir`) is no longer blocked on this.** Phase 1 exercised `tart run --dir <name>:<path>` (virtio-fs mount) successfully at the `tart run` level, but couldn't confirm the mount landed correctly inside the guest because the only inspection tool available (`tart exec`) was the thing that failed. With SSH now the transport, verifying the `--dir` mount is unblocked — a future spike can just SSH in and `ls`/`cat` the mounted path directly.

**Operational notes surfaced in passing:** Tart's own install caveats recommend shortening the default DHCP lease time (86,400s → 600s) when running many ephemeral VMs per day, and offer a `--net-softnet` isolation mode for exactly that "lots of short-lived VMs" pattern. Cirrus Labs' base image ships a default `admin`/`admin` guest account — now load-bearing (it's the SSH path this decision relies on) rather than just a debugging convenience, which raises the stakes on the credential-hygiene item already flagged: rotate or scope it down in the baked `gsd-tester-macos-tart` image rather than shipping the base image's default unchanged.

### Decision 5 — Memory ceiling is the concrete fix for the recurring OOM failure

Whichever transport shape Decision 4 lands on, every Tart-backed run sets a hard memory ceiling via `tart set --memory <MB>` before boot, playing the same role `internal/dispatch.DefaultMemory` plays for the Docker Benches (ADR-0021). This is the direct fix for the repeated "a leaking or spawning test runs the host Mac out of memory" failure on the current bare-metal macOS Runner: the VM's memory pool is hypervisor-enforced, so a runaway process inside it is capped at the VM's allocation and cannot touch the host's RAM — the same protection the Linux and Windows Benches have had since ADR-0021, now available for genuine macOS execution too.

**Partially verified, Phase 1 (2026-09-06):** `tart set gsd-spike-vm --memory 4096` followed by `tart get gsd-spike-vm --format json` confirmed the config-level cap took (`"Memory": 4096`) on a real cloned VM. The guest-side effect (e.g. `sysctl hw.memsize` reporting 4096 MB from inside the running VM) was **not** independently observed in this pass, for the same reason as Decision 4's gap: the only way to query the guest is `tart exec`, which did not work. The config-level mechanism is real; empirical proof of in-guest enforcement is still outstanding, bundled with the same follow-up as Decision 4.

### Decision 6 — Orchestration shape: a separate `internal/tartpipeline`, not a Runtime branch inside `internal/pipeline`

**(New, 2026-09-07.)** Getting `RuntimeTart` from "selectable config value" (Decision 1, done) and "SSH transport exists" (Decision 4, done) to "a Bench configured with `runtime = \"tart\"` actually runs the pipeline" requires reconciling a real structural mismatch: `internal/pipeline.Pipeline`'s 8 legs (`CheckImageVersion → StartContainer → CopyWorktree → NpmCI → Build → RunTests → Drain → Parse`) are built entirely around Docker's specific capabilities, several of which Tart does not have an equivalent for at all:

- **`docker cp` copies into an already-running container.** Tart's `--dir` share (the copy-in mechanism, per Decision 4's amendment) must be attached at `tart run` boot time — copy-in has to happen *before* boot, not after. `CopyWorktree` and `StartContainer` are not just reorderable for Tart, they're the same operation.
- **`docker image inspect --format` reads an OCI label without running anything.** Tart has no confirmed equivalent (Decision 3) — checking the version sentinel requires the guest to already be booted and reachable via `tartexec.Exec`, so `CheckImageVersion` necessarily happens *after* boot for Tart, not before it.
- **Newly identified in this pass: Docker's remote-Bench transparency doesn't exist for Tart at all.** `internal/dockerexec.Run` works against a remote Bench because the *local* `docker` CLI, pointed at `DOCKER_HOST=ssh://<bench>`, transparently tunnels the file bytes for `docker cp` over that connection — the Dev Workstation never needs its own explicit file-transfer step. Tart has no daemon to point at remotely (Decision 4's whole premise). So getting the PR-merged worktree from the Dev Workstation onto the Bench's filesystem (where it can then be `--dir`-mounted into the guest) needs an **explicit Workstation→Bench transfer** — a genuine new primitive, not a reordering of existing ones. Likewise pulling results back out needs an explicit Bench→Workstation transfer. This is additive to `internal/tartexec`: a one-hop `CopyToBench`/`CopyFromBench` (plain `scp`, mirroring `RunTart`'s one-hop SSH shape), distinct from `Exec`'s two-hop guest command execution.
- **`internal/images.EnsurePresent` is Docker-specific top to bottom** (`dockerPull`, `imagePresent`, a Dockerfile-based fallback build) and runs *before* `pipeline.New` is even constructed, at the single call site in `internal/runner/runner.go`'s `work()` closure. A Tart-aware equivalent (`tart pull`-based presence check) is needed at that same call site — with fallback-build intentionally **out of scope**: unlike Docker's Dockerfile fallback, triggering a full Packer bake (Decision 3/the bake pipeline) from inside a live test run is a different order of operation than a `docker build`, and is not something this decision authorizes doing ad hoc mid-run.

**Decision:** a new package, `internal/tartpipeline`, implements the Tart-backed execution path as its own `Pipeline` type — not a `Runtime`-conditional branch inside `internal/pipeline`'s existing leg methods. This mirrors ADR-0027's own precedent directly: that ADR deliberately kept the Pipeline and Watchdog execution engines separate rather than unifying them behind one interface, specifically because each composes the shared Preparation primitives in a different order for good reason. The same reasoning applies here a third time — `tartpipeline.Pipeline` composes different primitives in a different order (boot-with-mount instead of start-then-copy, post-boot sentinel check instead of pre-boot) for the same kind of good reason (Tart's actual capabilities, not a preference).

**What stays identical, on purpose — this is the "callable the same way" requirement:** `tartpipeline.Pipeline` reuses `internal/pipeline`'s exported `Event`, `Leg` (and its constants — `LegCheckImageVersion`, `LegStartContainer`, etc.), `LegError`, and `ErrLegSkipped` types rather than inventing parallel ones. It emits the same `EventLegStart`/`EventLegSuccess`/`EventLegFailure`/`EventChildOutput` shape on the same 8 named legs (even though, mechanically, `StartContainer` and `CopyWorktree` fire as one combined boot operation on the Tart side — both leg events still fire, in order, so the renderer and the user see the same per-OS report shape regardless of backend). `New(...)`, `RunAll(ctx) (report.Report, error)`, `DrainedPath() string`, and `Report() report.Report` mirror `pipeline.Pipeline`'s signatures closely enough that `internal/runner/runner.go`'s single call site (`work()`, currently `pipeline.New(...)` → `pl.RunAll(ctx)` → `pl.DrainedPath()`) becomes a `bench.Runtime`-conditional constructor choice — the only branch point, matching how `RuntimeBin()` is already the only branch point between `RuntimeDocker` and `RuntimeContainer` today. Everything upstream (`internal/runner`'s scheduling, the renderer, the report aggregation, the CLI) needs zero Tart-specific knowledge beyond that one constructor choice.

**Sequencing:** `internal/tartexec`'s `CopyToBench`/`CopyFromBench` addition lands first (small, mirrors the existing `RunTart`/`Exec` shape and tests). `internal/tartpipeline` plus the Tart-aware `EnsurePresent` equivalent and the `runner.go` integration land as a follow-up once those primitives exist to build on.

### Decision 7 — Reaper parity for leaked Tart VMs: a required side-channel state file, not a Docker-label equivalent

**(New, 2026-09-07.)** `tartpipeline.Pipeline.Cleanup`'s own doc comment flagged the gap explicitly from the moment Decision 6 shipped: "A run that crashes before RunAll's deferred Cleanup fires (process killed, host rebooted) leaks a running Tart VM with no automated sweep to catch it." Docker Benches have had this problem solved since ADR-0021/ADR-0029: every run container is `--name`/`--label`led with a run-id, branch slug, and deadline, and `internal/reaper.Sweep` reaps any labeled container whose deadline has passed on next contact with the Bench. Tart VMs had no equivalent identity at all.

**The core obstacle: Tart carries no metadata field whatsoever.** This was independently confirmed against real hardware, not assumed: `tart get <name> --format json` on a real, live-cloned VM returns exactly `Display`, `Memory`, `OS`, `Disk`, `Size`, `DiskFormat`, `State`, `CPU`, `Running` — no labels/metadata field. `tart list --format json` (enumerating every VM on a Bench, the primitive a sweep needs) returns the same shape per-VM plus `Name`/`Source`/`Accessed`, again with nothing to carry a branch/run/deadline. There is no OCI-label-style round-trip available the way Decision 3 explored for image versioning — Tart simply has nowhere to put this data on the VM object itself.

**Decision:** `internal/tartpipeline.Pipeline.StartContainer` writes a small JSON side-channel state file to the Bench's filesystem — `/tmp/gsd-test-tart-state/<vmName>.json`, containing `{"run_id":...,"branch_slug":...,"deadline_ms":...}` (the same `DeadlineMs` `internal/runner`'s `buildContainerIdentity` already computes for Docker, reused as-is, not a separate Tart-specific TTL). A new package, `internal/tartreaper`, mirrors `internal/reaper`'s `Overdue`/`OwnedBy`/`Sweep` shape: it lists `gsd-tart-*` VMs via `tart list --format json`, reads each one's state file over the same one-hop SSH primitive (`internal/tartexec.RunShell`, a new addition alongside `RunTart` for running an arbitrary shell command — not just `tart <args>` — on the Bench), and reaps the union of a branch-scoped tier and a safety-net tier, exactly like `reaper.Sweep`. `reaper.SafetyNetGrace` is imported and reused directly from `internal/reaper`, not redefined, so the two runtimes' reapers can never silently drift apart on how long the cross-branch diagnostic window is.

**The state-file write is REQUIRED (fails the leg), not best-effort.** This is the load-bearing invariant the whole design depends on: `StartContainer` sets `p.vmStarted = true` immediately after `clone` succeeds (unchanged from Decision 6), so if the state-file write itself then fails, `Cleanup` still fires — in the SAME run, immediately — and stops+deletes the VM before the process ever exits. The consequence: a Tart VM can only ever be left running on a Bench past its own pipeline's lifetime if the state-file write SUCCEEDED. Equivalently, `internal/tartreaper.Sweep` can treat any `gsd-tart-*` VM found WITHOUT a readable state file as categorically out of scope — not "unlabeled, sweep it anyway with an unknown deadline," but "cannot have leaked via this pipeline's normal path; leave it alone; an operator can remove it by hand." This mirrors Docker's own `Overdue` behavior (a container with `DeadlineMs == 0` — no deadline label — is never reaped) but is stronger here: for Docker, an unlabeled container is merely pre-ADR-0029 and gets no deadline; for Tart, an unlabeled VM is evidence that the one path capable of producing a labeled leak (this pipeline) did not do so, because it would have self-cleaned in-run.

`Cleanup` was updated to match: it now also issues a best-effort `rm -f` of the VM's own state file after stop+delete (mirroring its existing error-discarding shape for the stop/delete calls themselves), so a normally-completing run leaves no stale state file behind for a later sweep to misread.

Both `internal/runner`'s automatic pre-run sweep (`sweepStaleTartVMs`, run alongside the existing Docker-side `sweepStaleContainers`, before `schedule.Run` starts) and the manual `gsd-test sweep` command (dispatching per-Bench by `Runtime`) now cover Tart Benches with the same "reap on next contact" durability and the same reported output shape Docker Benches have had since ADR-0029.

## Consequences

- gsd-test-runner gains its first execution path where macOS itself is the sandboxed test guest — the original ask behind issue #8, met by neither the original Apple Containers plan nor the current Docker-on-macOS amendment.
- The bare-metal macOS Runner's unbounded-memory failure mode gets a real fix for Benches that opt into `RuntimeTart`, without forcing every macOS Bench operator to adopt it — Decision 2 keeps Docker-on-macOS available as the low-friction default.
- New operational and maintenance surface: Tart must be installed on any Bench that opts in (e.g. `brew install cirruslabs/cli/tart`), and a macOS Tester VM image must be built, versioned, and kept in sync with the Linux/Windows Tester Images' Node version and Reporter — this is genuinely new work, not free.
- Apple's macOS SLA (≤2 additional instances, Apple-branded hardware, development/testing purposes) is satisfied by this project's existing "developer's own hardware" Bench model (ADR-0007). It would not be satisfied by scaling this into a shared, multi-tenant, non-Apple-hardware macOS VM pool — this ADR does not authorize that shape, and a future ADR would be needed before pursuing it.
- Decisions 3 and 4 were resolved by a documentation-only spike (Context7 against Tart's own docs), then genuinely put to the test hands-on (Phase 1) on a real Apple Silicon Mac (`studio-mac-mini.local`): installed Tart 2.32.1, pulled a real `ghcr.io/cirruslabs/macos-tahoe-base:latest` image (27.3 GB compressed, 50 GB on disk), cloned it, and booted it. This caught one real Phase 0 error (Tart *does* have an OCI-label mechanism, via `tart push --label` — see Decision 3's correction) and surfaced one real, still-open blocker: **`tart exec` failed against the live guest** (exit 125, no output) despite the Guest Agent confirmed running with the right flags and everything else about the VM working correctly (booted, got an IP, reachable via direct SSH with Cirrus Labs' default `admin`/`admin` credentials). See Decision 4 for the full account and the working hypothesis (an unconfirmed macOS Application Firewall prompt with no UI to click through in headless mode).

  **Practical effect on Decisions 3-5:** the OCI-registry pull/clone/push mechanics (Decision 3) and the `tart set --memory` config-level cap (Decision 5) are now real, empirically confirmed facts, not documentation claims. Decision 4's exec transport changed conclusion, not just confidence: a follow-up root-cause research pass (Phase 2, same day) couldn't pin down exactly why `tart exec` failed, but found that Cirrus Labs' own reference CI tool (`gitlab-tart-executor`) doesn't use `tart exec` either — it uses SSH exclusively, the same default credentials already confirmed working here. That's decisive enough on its own: **Decision 4 now specifies SSH, not `tart exec`, as the transport**, without needing the underlying `tart exec` mechanism ever explained. **Implementation is no longer blocked on an open question** — disk space, CLI-shape uncertainty, and the exec-transport choice are all resolved as of this pass; only the custom-image bake process (Decision 3) remains genuinely unverified. (The disk-space concern was a red herring: `df`/`diskutil` under-reported free space relative to APFS's purgeable-space pool, which Finder's Storage view — and an actual Trash-empty — confirmed was far larger than the tools initially suggested.)
- `RuntimeContainer`/Apple-Containers plumbing remains in the codebase, unused, as a historical marker that the path was evaluated and rejected on its technical merits. A future cleanup ADR could remove it now that this ADR gives a permanent reason it won't be adopted, but that removal is out of scope here.
- Cirrus CI, the hosted CI product built by the same team as Tart, is shutting down. This does not affect adopting Tart itself — Tart is a separately usable, self-hosted open-source CLI, and this project's Bench model was never going to depend on a hosted CI SaaS (ADR-0007) — but it is a signal of ecosystem consolidation worth tracking if Tart's own maintenance cadence ever becomes a concern.

## Alternatives considered

- **Do nothing; keep Docker-on-macOS as the only macOS Bench option.** Rejected: four months in, it still hasn't closed the "test macOS-native code" ask behind issue #8, and it does nothing for the bare-metal Runner's unbounded-memory failures for anyone not using it.
- **Wait for Apple Containers to add macOS-guest support.** Rejected: no roadmap or announcement exists; available community discussion suggests the omission may be deliberate rather than a near-term gap. Blocking on it indefinitely repeats ADR-0020's original mistake of over-specifying an unready runtime, except this time there is no version number to wait for.
- **Hand-roll Virtualization.framework directly (a Go/cgo binding or a small Swift helper) instead of adopting Tart.** Rejected for now: Tart already solves restore-image management, auxiliary-storage provisioning, and clone-based ephemeral VM lifecycle. Reimplementing that is substantially more work for no clear benefit over shelling out to a well-maintained CLI — the same posture this codebase already takes toward `docker` and `container` (ADR-0014). Revisit only if Tart proves to be an operational dead end.
- **Depend on Cirrus CI's hosted macOS VM product instead of self-hosting Tart.** Rejected: Cirrus CI (the hosted SaaS) is shutting down, and this project's Bench model is self-hosted developer hardware by design (ADR-0007) — there was never a plan to depend on a hosted CI SaaS here.
- **Lock in Decisions 3 and 4 now instead of leaving them open.** Rejected: neither has been prototyped against real Tart tooling. Guessing at the image-distribution and exec-transport shape risks repeating ADR-0020's original-decision-then-amendment cycle for a second runtime; an explicit spike is cheaper than a wrong lock-in.
